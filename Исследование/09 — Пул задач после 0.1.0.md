# Пул задач после 0.1.0

Справочник шести задач. Порядок и причины лежат в [[08 — Роадмап после 0.1.0]]. Здесь только границы, имена и условия готовности.

Команда меняет состояние и возвращает `None`. Запрос возвращает состояние и не меняет его. Тест на настоящем Postgres, один act, схема AAA. В лог и в текст метрик не попадают `args`, `result` и `errors`.

Общие правила CLI, те же, что у `akadze migrate`. Переменная `AKADZE_DATABASE_URL`. Код выхода 2, если она пустая. Код выхода 1 при ошибке базы. Пароль в сообщении заменён. Код выхода 0 при успехе.

## W3-1. Список задач

Запрос. Зависит от 0.1.0. В одном релизе с W3-2 и W3-3.

`list_jobs(engine, *, queue: str | None, state: str | None, limit: int) -> tuple[JobSummary, ...]`

`JobSummary` содержит `id`, `task`, `queue`, `state`, `priority`, `attempt`, `max_attempts`, `run_at`, `started_at`, `finished_at`. Полей `args`, `result`, `errors`, `meta` нет.

`limit` по умолчанию 50. `limit` меньше 1 или больше 1000 поднимает ошибку. Неизвестное `state` поднимает ошибку. Фильтр `queue` и фильтр `state` необязательны. Порядок строк начинается с `priority` по убыванию, затем идёт `run_at`, затем `id`.

CLI: `akadze jobs list`. Флаги `--queue`, `--state`, `--limit`. Одна задача на строку.

Готово, когда тест вставляет строки в разных очередях и состояниях, один раз вызывает `list_jobs` и проверяет фильтр, порядок и предел. Тип результата не содержит аргументов.

## W3-2. Повтор failed

Команда. В одном релизе с W3-1. Код W3-1 не требуется.

`requeue(session, job_id) -> None` выполняется в транзакции вызывающего, как `request_cancel`.

Команда действует только на `state = 'failed'`. Она выставляет `state = 'queued'`, `run_at = now()`, пустые `worker_id`, `started_at`, `finished_at`, `cancel_requested_at`. Она сохраняет `attempt`, `run_count`, `errors`, `args`. Она ставит `max_attempts = greatest(max_attempts, attempt + 1)`.

Если строки нет или состояние другое, команда поднимает ошибку и ничего не пишет. Если срабатывает индекс `jobs_unique_key_active_idx`, команда поднимает `DuplicateJob` из savepoint. Строка остаётся `failed`. Транзакция вызывающего остаётся жива.

`cancelled`, `queued`, `running` и `succeeded` эта команда не меняет.

CLI: `akadze jobs requeue JOB_ID`.

Готово, когда тест доводит задачу до `failed` на потолке попыток, один раз вызывает `requeue` и затем видит успешный claim. Отдельный тест оставляет `cancelled` как был. Отдельный тест ловит `DuplicateJob` и проверяет, что `failed` на месте.

## W3-3. Пауза очереди

Команды. В одном релизе с W3-1.

Таблица `akadze.queue_pauses`:

- `queue text` primary key
- `paused_at timestamptz not null default now()`

`pause_queue(session, queue) -> None` вставляет строку. Повторный вызов для той же очереди не ошибка и не двигает чужие задачи. `resume_queue(session, queue) -> None` удаляет строку. Вызов для очереди без паузы не ошибка.

Claim не выбирает очередь, которая есть в `akadze.queue_pauses`. Задачи в `running` дорабатывают до своего перехода. `enqueue` в паузу пишет обычную строку `queued`. Periodic тоже может писать. Эти строки ждут `resume_queue`.

CLI: `akadze queues pause NAME` и `akadze queues resume NAME`.

Готово, когда при паузе воркер забирает ноль задач из этой очереди и забирает задачу из другой. Снятие паузы снова даёт claim. Задача, которая была `running` в момент паузы, доходит до `succeeded`.

## W3-4. Конкурентность по ключу

Второй релиз. Начинается после тега релиза с W3-1, W3-2 и W3-3.

Колонка `akadze.jobs.limit_key text`, пустая по умолчанию.

Таблица `akadze.limits`:

- `key text` primary key
- `max_running int not null`
- проверка `max_running >= 1`

`set_limit(session, key, max_running) -> None` записывает одну строку на ключ и заменяет прежнее `max_running`. `using(..., limit_key: str | None = None)` передаёт ключ в постановку. Число N в `using` не передаётся.

Пустой `limit_key` означает отсутствие лимита. Ключ без строки в `akadze.limits` не берётся в claim и остаётся `queued`.

Claim не выбирает и не блокирует задачу, у которой число `running` с тем же `limit_key` уже равно `max_running`. Следующая подходящая задача той же очереди с другим ключом или без ключа входит в ту же пачку. Ожидание не меняет `attempt` и `run_count`.

Готово, когда при `max_running = 1` две задачи с одним ключом дают одно `running`, вторая остаётся `queued`, а третья без ключа в этой же очереди переходит в `running`. После `succeeded` первой вторая берётся следующим claim.

## W3-5. Частота стартов по ключу

Третий релиз. Начинается после тега релиза с W3-4.

В `akadze.limits` добавляются `max_starts int` и `window interval`. Пустые значения означают, что частотного лимита нет. `max_starts` меньше 1 команда отвергает. Окно должно быть положительным. Иначе команда отвергает запись.

`set_limit` принимает эти поля отдельно от `max_running`. Одна команда не обязана задавать оба лимита сразу.

Старт считается успешным claim. Журнал стартов не читает всю историю `akadze.jobs` на каждом claim. Старые отметки удаляются, и горячая таблица задач от них не растёт.

Claim, который не влез в окно, оставляет задачу `queued`. Он не увеличивает `run_count` и не увеличивает `attempt`. Задача с другим `limit_key` или без ключа в той же очереди по-прежнему берётся.

Конкурентность из W3-4 продолжает действовать. Оба отказа оставляют задачу незаблокированной.

Готово, когда при `max_starts = 1` и окне в одну минуту второй claim того же ключа не берёт задачу, а claim другого ключа берёт. По истечении окна первый ключ снова берётся. `attempt` ожидающей задачи не меняется.

## W3-6. Текст метрик

Четвёртый релиз. Начинается после тега релиза с W3-5.

Модуль не импортируется из корня пакета. Зависимость клиента метрик не входит в установку по умолчанию.

`render_metrics(engine) -> str` возвращает текст Prometheus. Пакет не открывает сокет.

Серии, и только они:

- `akadze_jobs` с метками `queue` и `state`, значение из числа строк
- `akadze_queue_lag_seconds`, одно значение, секунды lag из `queue_snapshot`, либо отсутствие серии, если lag пустой
- `akadze_worker_busy`, одно значение, число `running`
- `akadze_queue_paused` с меткой `queue`, значение 1 для строки в `akadze.queue_pauses`

В тексте нет аргументов, результатов и текстов ошибок.

Готово, когда тест вставляет известное число задач, ставит одну очередь на паузу и находит эти числа в строке `render_metrics`. Отдельная проверка: строка результата не содержит аргумент задачи.

## Что в трекер не заводится

Следующие темы не получают номер, пока явно не изменён [[08 — Роадмап после 0.1.0]].

- Сахар цепочки, group, chord и блокирующее чтение результата
- `LISTEN/NOTIFY` и отдельный путь на голом asyncpg
- HTTP, веб-интерфейс, трейсинг
- Расписания, которые редактируются без деплоя
- Durable-шаги, секционирование `akadze.jobs`, шифрование аргументов
- Совместимость с протоколом Celery и адаптер `django.tasks`
