# Пул задач после 0.4.0

Справочник задач Wave 5. Черновик. Порядок и причины — в [[Роадмап после 0.4.0]]. Здесь только границы, имена и условия готовности.

Команда меняет состояние и возвращает `None`. Запрос возвращает состояние и не меняет его. Тест на настоящем Postgres, один act, схема AAA. В лог и в текст метрик не попадают `args`, `result` и `errors`.

## W5-1. `max_attempts` на задачу

- [x] Сделано в 0.4.1 (#33)

Аддитивное расширение `Task.using(...)`. PR #33.

`using(..., max_attempts: int | None = None)`. `None` — значение из определения задачи, как сейчас. Число записывается в `akadze.jobs.max_attempts` этой строки. Значение вне `1..2147483647` (тип колонки `int4`) даёт `EnqueueError` при постановке, строка не создаётся — проверка лежит в `insert_job` рядом с проверкой `priority`, так её ловит тот же `except EnqueueError`. `@app.task` и `app.register` по-прежнему проверяют потолок задачи при регистрации (`AkadzeError`). Periodic по-прежнему ставит задачи с потолком из определения. Схема не меняется.

Готово, когда тест ставит задачу без override и с override и видит в строке ожидаемый потолок. Отдельный тест: `0`, `-1` и `2**31` отвергаются как `EnqueueError`, строк нет. Отдельный тест: задача, объявленная с `max_attempts=1` и поставленная с `2`, после первой ошибки снова `queued`. Отдельный тест: задача с `5`, поставленная с `1`, после первой ошибки `failed`.

## W5-2. Критерии Beta и политика версий

- [x] Сделано: [[12 — Публичная поверхность и критерии Beta]]; тест состава `akadze.__all__` в пакете. Вышло в 0.5.0.

Документ (explanation) и, при необходимости, тест.

Публичная поверхность — это:
- имена из `akadze.__all__` и их сигнатуры;
- подкоманды и флаги CLI, коды выхода;
- схема `akadze.*` в той части, которую читают ops-запросы и документация;
- текст серий из `akadze.metrics`.

Всё прочее (модули с `_`, SQL внутри воркера) — внутреннее.

Политика версий до 1.0: минор — волна или ломающее изменение; патч — исправления и небольшие аддитивные изменения, которые нужны потребителю раньше волны. Ломающее изменение помечается `!` в коммите и строкой в release notes.

Критерии Beta: поверхность выше записана; минимум один потребитель в проде без обходных путей; нет открытых багов про потерю или двойной запуск задачи; how-to миграции с Celery готов.

Готово, когда заметка с этими пунктами принята владельцем. Если владелец просит, тест сверяет `akadze.__all__` со списком из заметки.

## W5-3. How-to «Миграция с Celery»

- [x] Сделано в 0.4.1 (#36): раздел «Celery migration» в README пакета

Документ в README пакета или в `docs/` пакета (решение владельца). Харнесс хранит только решение, не текст гайда.

Покрывает: `@shared_task` → `app.register`; `apply_async(countdown/eta)` → `using(delay/run_at)`; `retry(countdown)` → `Retry` / `Snooze`; `celery beat` → periodic в воркере или `add_schedules`; `rate_limit` и пулы → `limit_key`; `chain` → постановка на `complete_tx`. Отдельно — чего нет и почему: canvas, результат через `.get()`, Redis/Rabbit.

Готово, когда каждый пример в гайде соответствует API текущей версии и раздел «чего нет» ссылается на решения харнесса без копирования их текста.

## W5-4. Cron в таймзоне

- [x] Сделано (#38), вышло в 0.5.0. Правило DST при реализации уточнено (см. ниже): вместо «весной не срабатывает» — сдвиг на длину перехода, как у классического cron.

Аддитивная опция расписания.

`@app.periodic(..., timezone="Europe/Moscow")`, то же поле в `add_schedule` и `ScheduleSpec`. `None` — UTC, как сейчас. Имя зоны — IANA, проверяется через `zoneinfo` при регистрации; неизвестная зона — `AkadzeError`. Для `every` зона не нужна и отвергается.

Cron считается в локальном времени зоны, слот хранится в `timestamptz`. DST — по правилам классического cron. Осенью запись с фиксированным часом срабатывает один раз (первый проход), запись с `*` в поле часа работает в обоих проходах. Весной фиксированное время внутри «дыры» срабатывает со сдвигом на длину перехода (02:30 → 03:30), чтобы дневная задача не терялась. Дедупликация слотов не меняется; если сдвинутый слот совпал с другим слотом того же расписания, срабатывание одно. croniter сам считает зоны с ошибкой (двойной слот осенью), поэтому пересчёт делает akadze.

Готово, когда тест с фиксированным `now` видит предыдущий слот `0 9 * * *` в `Europe/Moscow` как 06:00 UTC; тест на весенний и осенний переход в зоне с DST (`Europe/Berlin`) даёт ноль и один слот; неизвестная зона и `timezone` при `every` отвергаются.

## W5-5. Политика backoff и джиттер

- [x] Сделано (#39), вышло в 0.5.0. Дополнительно: задержки зажаты в `[0, 365 дней]` (иначе завершение падало на переполнении interval), отрицательный `Retry`/`Snooze` = «сейчас», задачи упавшего воркера rescue ставит с джиттером, async-политика отвергается, `@app.periodic(backoff=...)`, тип `akadze.BackoffPolicy`.

Аддитивная опция задачи и смена кривой по умолчанию.

`@app.task(..., backoff=fn)` и `app.register(..., backoff=fn)`, где `fn(attempt: int) -> timedelta`. `Retry(delay)` по-прежнему главнее. Без `backoff` — экспонента `2^(attempt-1)` с потолком, как сейчас, но с джиттером: случайно в `[50 %, 100 %]` от значения. Отрицательное или нулевое значение от `fn` даёт минимальную задержку, как у `Retry`. Исключение в `fn` не роняет воркер: берётся кривая по умолчанию.

Готово, когда тест с `backoff=lambda n: timedelta(minutes=n)` видит `run_at` через `attempt` минут; тест на кривую по умолчанию видит задержку в границах `[0.5, 1] · 2^(n-1)`; тест на исключение в `fn` даёт кривую по умолчанию.

## W5-6. Пакетная постановка

- [x] Сделано (#40), вышло в 0.5.0. Вся пачка — под одним savepoint (сбой во втором куске или в хуке ничего не оставляет). 10 000 задач: 0,07 с против 16 с циклом `enqueue`.

Команда.

`await task.using(session=..., ...).enqueue_many(items)` — `items`: итерируемое из `Mapping[str, Any]`, аргументы по имени, как у `enqueue`. Опции `using()` общие для всех строк. Одна вставка на пачку (внутри — куски, чтобы не упереться в лимит параметров), в транзакции вызывающего. Все аргументы проверяются до вставки: одна плохая строка — `EnqueueError`, не вставлено ничего. Пустой список — ничего не делает. `unique_key` вместе с `enqueue_many` — `EnqueueError` (ключ задаётся на одну задачу). Хук `on_enqueue` вызывается на каждую строку.

Готово, когда тест ставит 1000 задач одним вызовом и видит 1000 строк; тест с одной невалидной строкой видит `EnqueueError` и ноль строк; тест `unique_key` + `enqueue_many` отвергается; тест хука видит вызов на каждую строку.

## W5-7. Метаданные задачи и поиск

- [x] Сделано (#41), вышло в 0.5.0. `JobSummary.meta` — только чтение и вне хеша (сводка остаётся хешируемой); `Job.meta` виден хукам. NaN, NUL и не-str ключи на любом уровне — `EnqueueError`. Миграция `005` с `IF NOT EXISTS`, чтобы большой таблице индекс можно было построить заранее `CONCURRENTLY`.

Аддитивное поле и фильтр запроса.

`using(..., meta={...})` пишет JSON-объект в `akadze.jobs.meta` (ключи — строки, значения — JSON). Не для секретов и не для аргументов: это ярлыки для операций (`tenant`, `order_id`). `list_jobs(..., meta={...})` фильтрует по вхождению (`meta @> :meta`). `JobSummary` получает поле `meta`. CLI: `akadze jobs list --meta key=value` (повторяемый). Индекс GIN на `meta` — миграцией, чтобы фильтр не сканировал таблицу.

Готово, когда тест ставит задачи с разными `meta` и `list_jobs(meta=...)` возвращает только совпавшие; `meta` не-объект отвергается `EnqueueError`; CLI печатает `meta` в строке и фильтрует.

## W5-8. Справедливая выборка по ключу

- [x] Сделано (#42), вышло в 0.5.0. При реализации правило уточнено: «по кругу» в каждом claim с нуля не справедливо в устойчивом режиме (слоты освобождаются по одному, много воркеров). Очередь задачи = число уже `running` задач её группы в этой очереди по кластеру + её место в группе; слот получает наименее загруженная группа.

Новый режим claim, включается флагом воркера: `Worker(..., fair=True)` и `akadze worker --fair`. По умолчанию порядок прежний — так поведение существующих установок не меняется.

Задачи с одинаковым непустым `limit_key` образуют группу. Сейчас claim берёт по `priority, run_at, id` по всей очереди, и группа с огромным хвостом забирает все слоты. После: внутри одного приоритета claim чередует группы — сначала по одной самой старой задаче каждой группы, потом по второй, и так далее. Задачи без ключа считаются одной группой. Приоритет по-прежнему главнее справедливости. Лимиты W3-4/W3-5 работают как раньше.

Готово, когда тест ставит 100 задач ключа `a` и 2 задачи ключа `b`, и claim на 2 слота с `fair=True` берёт одну `a` и одну `b` (без флага — две `a`); тест приоритета: задача с большим `priority` берётся раньше чужой группы; замер claim на 100 тыс. строк в `queued` записан в PR и не хуже текущего больше чем вдвое.

## W5-9. Claim без скана всего хвоста

- [x] Сделано для порядка по умолчанию (#43), вышло в 0.5.0: claim сначала из головы очереди (`limit × 4` строк), полный скан — только если голова не дала `limit`. Около 20 мс вместо ~330 мс на 100 тыс. Режим `fair` пока на полном скане (~300 мс на 100 тыс.) — в следующую волну. Вариант с обходом ключей по индексу отвергнут на саморевью: мог морить ключи голодом.

Перф, без нового API. Найдено при замере W5-8: на 97 тыс. готовых задач один claim стоит около 260 мс, потому что `ready` берёт все готовые строки очереди, а окна и лимиты считаются по ним всем.

Направление: ограничить кандидатов (верх по `priority, run_at, id` с запасом на лимиты и справедливость) и подобрать индекс под этот порядок. Семантика лимитов и `fair` не меняется.

Готово, когда замер из W5-8 показывает claim на 100 тыс. строк в разы быстрее для обоих режимов, а тесты лимитов и `fair` проходят без изменений.
