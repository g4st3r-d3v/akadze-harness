### B1. Хук `on_transition` бросает исключение — тело выполняется снова

`_finish` вызывает хуки внутри транзакции исхода. `Worker._record` ловит только `DB_ERRORS`. Исключение хука откатывает переход, выходит из `_execute`, а `finally` убирает задание из `_inflight`. Строка остаётся `running` у этого же воркера (heartbeat жив, rescue её не трогает), и следующий `_spawn` через `running_jobs` запускает тело снова. Так повторяется без конца и без траты попыток. Каждый раз повторяются побочные эффекты тела.

Сейчас в docstring `Hooks` записано «хук не должен бросать». Варианты:

1. **Записать исход без хуков** и залогировать ошибку хука. Задание завершено, но гарантия «`on_transition` видит каждый переход» нарушается.
2. **Записать `failed` с ошибкой хука** (как `_record_unstorable`) — снова через хуки. Если хук падает и на этом, воркер останавливается (`_fatal`), задание подбирает rescue.
3. **Остановить воркер** сразу (`_fatal`). Задание вернёт rescue с тратой попытки. Rescue тоже вызывает хуки, так что сломанный хук остановит и его.

Рекомендация: 2. Хук остаётся частью транзакции (аудит не теряет переходов), повторного запуска тела нет, а сломанный хук виден как `failed` с понятной ошибкой.

### B2. PgBouncer в transaction-режиме

README и docs обещают, что `statement_cache_size=0` позволяет ставить PgBouncer в transaction-режиме. Но SQLAlchemy-диалект asyncpg готовит именованные statements (`__asyncpg_stmt_N__`), и документация SQLAlchemy для PgBouncer требует ещё уникальный `prepared_statement_name_func`. Не проверено. Нужен тест с PgBouncer в docker. Если подтвердится — добавить `prepared_statement_name_func` в engine, который строит `Akadze`, и строку в docs. Обещание из docstring `Akadze` уже убрано, в README и docs осталось.

### B3. `retention` короче `grace`

`prune` удаляет строку `periodic_runs`, которая ещё в окне `grace`, и следующий тик ставит тот же запуск второй раз. Варианты: `AkadzeError` в `Akadze(...)` при `retention <= grace`, или чистить `periodic_runs` по `max(retention, grace)`. Рекомендация: второе — ничего не ломает.

## Поведение, которое стоит выровнять

- **B4. Rescue игнорирует `backoff` задачи.** SQL `rescue` всегда берёт `2^attempt` с потолком 300 с. Задача с политикой «час между попытками» после потери воркера перезапускается через секунды. В docs и docstring `Worker` это уже записано как факт. Выровнять — передавать задержку из политики. Rescue работает в SQL пачкой, поэтому придётся считать задержку в Python по строкам.
- **B5. `requeue` не вызывает `on_transition`.** Переход `failed → queued` проходит мимо хуков. Записано в docstring `Hooks`. Выровнять — `requeue` принимает `hooks` (или app), но это меняет сигнатуру публичной функции.
- **B6. `errors` растёт без предела на пути rescue.** `push_error` держит последние 10 записей, а rescue дописывает `WorkerLost` без обрезки.
- **B7. Пространство `unique_key` общее** для всех задач и очередей, и `overlap=False` использует ключ `periodic:<name>` в нём же. Пользовательский ключ `periodic:report` молча блокирует расписание `report`. Записано в docstring `using`. Варианты: префикс, который пользователь не может занять, или отдельная колонка.
- **B8. У `@app.periodic` нет `priority`.** Расписание через `add_schedule` берёт приоритет задачи, а `@periodic` — всегда 0. Добавить параметр — аддитивно.

## Пропускная способность воркера

Отставание от PgQueuer ~2.3× на пустых заданиях (#63). Из профиля: на задание — перечитать строку перед стартом (fencing), транзакция исхода с хуками, всё через SQLAlchemy; цикл claim делает `_cancel_due` + `count_running` + claim + `running_jobs` на каждой итерации. Кандидаты: число running своего воркера брать из `_inflight`, а не запросом; `_cancel_due` реже, чем каждый цикл; завершать исходы пачкой, когда хуков нет. Каждый — с замером на `bench/compare.py`.

Шаг 1 (2026-11-04, PR #68, закрыт 2026-11-08): шаг отмены (`_cancel_due`) в цикле `serve` — не чаще раза в `poll_interval`. Саморевью: троттлинг держит `unique_key` отменённых `queued` до `poll_interval` (отменить и поставить заново → `DuplicateJob`) и оставляет такие строки в голове окна claim — PR отложен, правильнее B11 (индекс). Замер ниже остаётся как профиль. Профиль на 5000 пустых заданий, 20 слотов: цикл последовательный, 501 итерация × ~14 мс — это весь прогон; в итерации `_cancel_due` ~4 мс (O(queued): индекса под его условие нет), `count_running` и `running_jobs` по ~1.4 мс, claim ~7 мс. 10k заданий: 700/с → 795/с (медиана из 3, локально). Следующие шаги: `count_running` из `_inflight` (учесть `_stuck` из #67), claim возвращает свои строки вместо `running_jobs`, затем — меньше запросов на задание (fencing-чтение + `SELECT` перед `UPDATE` в `_finish`).

## Решения владельца (2026-11-12)

Владелец делегировал выбор («как лучше решишь»). Записано:

1. **Пакетная запись исходов — опция воркера.** `Worker(outcome_batch=None)` по умолчанию: каждый исход сразу, как сейчас. `outcome_batch=timedelta(milliseconds=10)`: исходы копятся и пишутся одной транзакцией раз в интервал или при наполнении пачки; CLI `--outcome-batch 10ms`. At-least-once одинаков. Хуки — по строкам в транзакции пачки, ошибка хука не откатывает пачку (п. 3).
2. **B11 — делать**: частичный индекс под шаг отмены, миграция 006, замер на 100k.
3. **B10 — единая политика ошибок `on_transition`**: каждый вызов хука — в своём savepoint (`Hooks.ran_transition`). Хук бросил в любом переходе воркера (claim, отмена, исход, остановка, rescue) → откатываются записи хука, сам переход проходит, ошибка в лог (только тип) и в метрику. Воркер из-за хука не останавливается. **Исход выполнения тоже**: правило B1 (`failed` с ошибкой хука, вышло в 0.6.2) заменяется — исход записывается как есть, ошибка хука в логе. Причина: тело уже отработало, `failed` для успешного задания вводит в заблуждение, и пакетной записи нужна та же политика. `on_enqueue` не меняется: ошибка откатывает постановку у вызывающего.
4. **Fencing-чтение перед стартом — оставить**; замерить его долю после пакетной записи и решать по цифрам.

Сделано по скорости (2026-11-12): #71 (claim возвращает строки, 746 → 863/с), #72 (запросы на задание — скомпилированный driver SQL, 746 → 824/с), оба в `main`.

## Новые находки (2026-11-04)

- **B10. Ошибка хука в остальных переходах.** #67 закрывает только исход выполнения. В `claim` (queued → running), `_cancel_due`, `_release` при остановке и `rescue` исключение хука останавливает воркер (`_step` и `shutdown` ловят только `DB_ERRORS`); хук, который всегда бросает на одном задании, останавливает rescue на всех воркерах. В `shutdown` такая ошибка заменяет исходный `_fatal`. Варианты: одна политика в `Hooks.ran_transition` (логировать и пропускать для служебных переходов) или как сейчас — сломанный хук останавливает всё. Нужно решение владельца.
- **B11. Индекс под шаг отмены.** `_cancel_due` читает все `queued` строки очереди. После #68 — раз в `poll_interval`, но при 100k в очереди это всё ещё скан. Частичный индекс `(queue) WHERE state = 'queued' AND (cancel_requested_at IS NOT NULL OR expires_at IS NOT NULL)` (миграция 006) делает его O(отменяемых). Нужен замер на 100k. Заменяет троттлинг из #68: отмена остаётся мгновенной. Миграция схемы — решение владельца.
- **B12. PEP 621.** `poetry check` предупреждает: `[tool.poetry.scripts]` и license classifier устарели. Перевести метаданные в `[project]`. Аддитивно для пользователей.
