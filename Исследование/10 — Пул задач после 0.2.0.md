# Пул задач после 0.2.0

Справочник задач Wave 4. Порядок и причины лежат в [[Роадмап после 0.2.0]]. История Wave 3 (сделана в `0.2.0`) — в [[09 — Пул задач после 0.1.0]]. Здесь только границы, имена и условия готовности.

Все четыре обязательные задачи **сделаны** и вышли в `0.3.0` (2026-10-11). Условия готовности оставлены как история приёмки. Фактические имена в коде отмечены у задач.

Команда меняет состояние и возвращает `None`. Запрос возвращает состояние и не меняет его. Тест на настоящем Postgres, один act, схема AAA. В лог и в текст метрик не попадают `args`, `result` и `errors`.

Общие правила CLI, те же, что у `akadze migrate`. Переменная `AKADZE_DATABASE_URL`. Код выхода 2, если она пустая. Код выхода 1 при ошибке базы. Пароль в сообщении заменён. Код выхода 0 при успехе.

## W4-1. CLI отмены задачи

- [x] Сделано в 0.3.0 (#25)

Команда уже есть: `request_cancel`. Нужны CLI и ops-дока. В одном релизе с W4-2…W4-4.

Семантика Python не меняется. `request_cancel(session, job_id) -> None` по-прежнему выставляет `cancel_requested_at = now()` для `state IN ('queued', 'running')` и ничего не возвращает. Воркер применяет отмену. Состояния `failed`, `succeeded`, `cancelled` эта команда не трогает.

CLI: `akadze jobs cancel JOB_ID`. Успех — код выхода 0. Сообщение об ошибке базы без пароля.

В README / how-to ops рядом с `jobs requeue` появляется тот же путь для cancel.

Готово, когда тест ставит задачу в `queued` (или доводит до `running`), один раз вызывает CLI или тот же путь, что CLI, и видит `cancel_requested_at` не пустым. Отдельная проверка: в тексте помощи / доки есть `jobs cancel`.

## W4-2. Список лимитов и снятие

- [x] Сделано в 0.3.0 (#25, #26). В коде `clear_limit(session, key)` и `akadze limits clear KEY`. Удаление строк `akadze.limit_starts` при снятии — fix после 0.4.0.

Запрос и команда. В одном релизе с W4-1.

`list_limits(engine) -> tuple[LimitSummary, ...]`

`LimitSummary` содержит `key`, `max_running`, `max_starts`, `window`. Других полей нет.

Порядок строк — по `key` по возрастанию.

`unset_limit(session, key) -> None` выполняется в транзакции вызывающего, как `set_limit`. Команда удаляет строку из `akadze.limits` с этим `key` и удаляет строки `akadze.limit_starts` с тем же ключом. Повторный вызов для отсутствующего ключа не ошибка. Пустой `key` команда отвергает.

**Claim после unset.** Отсутствие строки в `akadze.limits` больше не запрещает claim. Задача с непустым `limit_key` без строки политики берётся как задача без лимита. Пустой `limit_key` по-прежнему значит отсутствие лимита. Строка политики по-прежнему ограничивает конкурентность и частоту. Так снимается и капкан «удалил политику — задачи навечно `queued`», и прежний silent fail-closed для опечатки; видимость заданных ключей даёт `list_limits`.

CLI: `akadze limits list` и `akadze limits unset KEY` (допускается синоним `clear` вместо `unset`). Одна строка лимита на строку вывода. Запись лимита по-прежнему через Python `set_limit` (отдельный CLI `set` в эту задачу не входит, если не понадобится для симметрии — тогда флаг владельца).

Готово, когда тест записывает лимит, один раз вызывает `list_limits` и видит ключ и поля. Отдельный тест вызывает `unset_limit`, затем claim задачи с этим `limit_key` проходит без строки в `limits`. Отдельный тест: после `set_limit` и до `unset` конкурентность из W3-4 по-прежнему держит вторую задачу в `queued`.

## W4-3. Список воркеров

- [x] Сделано в 0.3.0 (#27)

Запрос. В одном релизе с W4-1.

`list_workers(engine) -> tuple[WorkerSummary, ...]`

`WorkerSummary` содержит `id`, `hostname`, `pid`, `queues`, `started_at`, `heartbeat_at`. Полей с секретами и DSN нет.

Порядок строк начинается с `heartbeat_at` по убыванию, затем `id`.

CLI: `akadze workers list`. Одна строка на воркера.

Готово, когда тест вставляет одну или несколько строк в `akadze.workers`, один раз вызывает `list_workers` и проверяет поля и порядок. Тип результата не содержит аргументов задач.

## W4-4. CLI текста метрик

- [x] Сделано в 0.3.0 (#27): `akadze metrics` и `akadze metrics render`

Обёртка над уже сделанным `render_metrics`. В одном релизе с W4-1.

Модуль `akadze.metrics` по-прежнему не импортируется из корня пакета. Серии те же, что в W3-6. Пакет не открывает сокет.

CLI: `akadze metrics` (допускается `akadze metrics render`). Печатает в stdout ровно строку `render_metrics(engine)`. Коды выхода — общие для CLI.

Готово, когда тест с известным снимком очереди запускает CLI-путь и находит в выводе ожидаемые серии; аргументы задачи в выводе отсутствуют.

## Опционально / не стартует

Следующий пункт **не** входит в обязательный скоуп Wave 4 и **не** заводится в трекер, пока владелец явно не поднимет флаг.

### Tracing hook (опционально)

Тонкий хук или запись `traceparent` в `meta` без зависимости OpenTelemetry по умолчанию. Без scrape-порта в пакете. Паритет витрины PgQueuer только по желанию владельца. Пока флага нет — статус «не начато».

## Что в трекер не заводится

Следующие темы не получают номер Wave 4, пока явно не изменён [[Роадмап после 0.2.0]] (и при необходимости [[08 — Роадмап после 0.1.0]]).

- Сахар цепочки, group, chord и блокирующее чтение результата
- `LISTEN/NOTIFY` и отдельный путь на голом asyncpg
- HTTP, веб-интерфейс, scrape-порт в пакете
- Расписания, которые редактируются без деплоя (YAML/TOML «Beat DB»)
- Durable-шаги, секционирование `akadze.jobs`, шифрование аргументов
- Совместимость с протоколом Celery и адаптер `django.tasks`
- Обязательный OTel/трейсинг (см. опциональный пункт выше)
